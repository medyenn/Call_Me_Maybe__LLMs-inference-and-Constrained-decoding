00 · Orientation

00The Big Picture

Before touching a single function, hold the whole shape of the program in your head. Five files, one job each, wired together by orchestrator.py:

__main__.py
parses CLI args, builds Config, loads the model, calls the pipeline
→
loader.py
reads & validates the two JSON input files + the tokenizer vocabulary
→
orchestrator.py
the per-prompt loop, shared time budget, wiring decoder → output
→
decoder.py
constrained decoding engine — the actual algorithm
→
output.py
parse, validate, coerce, fallback, write to disk

Everything in models.py (not pictured above because it has no verbs — it only has nouns) is the shared vocabulary every other file imports: Config, FunctionCatalog, FunctionCallResult. This is what lets the rest of the codebase talk about "a function" or "a result" without ever touching a raw dict.

Why this matters for defense

An evaluator's first question is often "walk me through what happens when I run this." Being able to name these five files, in this order, with one sentence each, before you even open a file, signals architectural understanding — not just "I can explain this function if you point at it."

01 · src/__main__.py

01The Entry Point

python -m src works because src/__main__.py exists — that's a Python convention: running a package with -m executes that package's __main__.py as the top-level script. Its only job is three things: turn argv into a validated Config, load the model, and hand control to run_pipeline — wrapped in exactly enough exception handling to guarantee the program never crashes with a raw Python traceback.

src/__main__.pybuild_config()
def build_config() -> Config:
    """Parse argv and build a validated Config."""
    namespace_obj = args_parser()
    overrides = {k: v for k, v in vars(namespace_obj).items() if v is not None}
    return Config(**overrides)

The trick worth noticing: every argparse flag defaults to None, not to the real default. vars(namespace_obj).items() turns the parsed namespace into a dict, and the dict-comprehension drops every key whose value is still None — i.e. every flag the user didn't pass. What's left, overrides, is only the flags the user actually typed. Those get splatted (**overrides) into Config(...), a pydantic model that already carries the real defaults (data/input/functions_definition.json, etc.) as class-level field defaults.

Why not just set argparse's default= directly?

Because then the "single source of truth" for defaults would be split across two places — argparse and Config — and they could silently drift. By making every CLI flag default to None and letting Config own the real defaults, there is exactly one place in the entire codebase that says "the default output path is data/output/function_calling_results.json."

Then main() does the un-glamorous but essential work:

src/__main__.pymain()
def main() -> None:
    config = build_config()
    try:
        sdk = Small_LLM_Model()
        run_pipeline(config, sdk)
    except PipelineError as e:
        print(f"Error: {e}", file=sys.stderr); sys.exit(1)
    except Exception as e:
        print(f"Unexpected error: {e}", file=sys.stderr); sys.exit(1)

PipelineError is not a class — it's a tuple of exception types ((OSError, ValueError, RuntimeError)) defined in orchestrator.py. Python's except accepts a tuple directly, so this one name documents, in one place, "these are the categories of failure this program considers expected and reports cleanly" — bad file paths (OSError), bad JSON/schema (ValueError), and internal invariants breaking (RuntimeError). The bare except Exception underneath is the safety net for anything that slipped the net — the subject's "never crash on the reviewer's machine" requirement, satisfied at the outermost layer.

02 · src/models.py

02Data Contracts — the Nouns of the Program

models.py has no algorithm in it. Its entire value is turning "a dict that came from a JSON file, which could contain absolutely anything" into a typed object that the rest of the program can trust without re-checking. This is pydantic's whole pitch: validate once, at the boundary, then treat the result as ground truth everywhere else.

ParamType & PYTHON_TYPE_BY_PARAM_TYPE

A Literal["string","number","integer","boolean"] plus a dict mapping each literal to its real Python type. This dict is imported by both decoder.py (to decide what characters are legal) and output.py (to decide what the final parsed value must look like) — one table, two consumers, so the decoder's idea of "number" and the validator's idea of "number" can never drift apart.

FunctionCatalog

Wraps list[FunctionDefinition] and builds a private _by_name index in a @model_validator(mode="after") hook — meaning the index is built exactly once, right after validation succeeds, and is guaranteed to exist for every catalog object that exists. It also rejects zero functions and duplicate names at load time, not three modules later when something looks up a name and silently gets the wrong function.

PromptItem / FunctionCallResult

The input and output record shapes. FunctionCallResult.parameters is typed dict[str, ParamValue] where ParamValue = Union[StrictBool, StrictInt, float, StrictStr] — the Strict* variants matter: without them, pydantic's normal type coercion would happily turn 1 into True or "3" into 3, silently hiding a decoder bug behind "helpful" coercion.

Config

Four fields, three Paths and a float — the complete, validated configuration surface of the whole program. Everything downstream takes a Config, never raw strings or raw argv.

Defend this

"Why pydantic and not just dicts?" — Because a malformed functions_definition.json (a missing "type", a duplicate function name, a non-string "name") fails loudly and immediately at fcts_loader(), with a message naming the exact file and the exact field. Without it, that same mistake would surface as a cryptic KeyError or AttributeError deep inside decoder.py, on a totally unrelated line, minutes into a run.

03 · src/loader.py

03Loading the World: Functions, Prompts, and the Vocabulary

json_loader is the one place json.load is ever called directly, and it exists purely to translate Python's default exceptions (FileNotFoundError, json.JSONDecodeError, OSError) into messages that name the offending file and, for JSON errors, the exact line and column. fcts_loader and prompt_loader are thin wrappers that feed the raw dict/list into the pydantic models from Section 02 and translate pydantic.ValidationError into a plain ValueError — collapsing two exception vocabularies (pydantic's and Python's built-ins) into the one PipelineError tuple that __main__.py already knows how to handle.

The interesting part: turning a raw vocab.json into usable text

The tokenizer's vocab.json does not map token IDs to plain text. It maps them to a byte-level, GPT-2-style display encoding: every one of the 256 possible byte values is remapped to a printable Unicode character so the vocabulary file itself can be valid, human-readable-ish JSON. The visible consequence is things like "Ġcat" instead of " cat" — that leading Ġ (U+0120) is standing in for a literal space byte.

src/loader.py_gpt2_byte_decoder()
def _gpt2_byte_decoder() -> dict[str, int]:
    byte_values = (
        list(range(ord("!"), ord("~") + 1))
        + list(range(ord("¡"), ord("¬") + 1))
        + list(range(ord("®"), ord("ÿ") + 1))
    )
    display_chars = byte_values[:]
    n = 0
    for b in range(256):
        if b not in byte_values:
            byte_values.append(b); display_chars.append(256 + n); n += 1
    return {chr(c): b for b, c in zip(byte_values, display_chars)}

Reading this the way you should be able to reconstruct it out loud: the "nice" printable ASCII and Latin-1 ranges (! through ~, ¡ through ¬, ® through ÿ) already map to themselves — byte 65 ("A") displays as "A". The remaining ~68 byte values that would otherwise render as control characters or be unsafe in JSON (byte 32, the space, is a good example — it's not in that "nice" range) get shifted up into the Unicode private-ish range starting at 256, so byte 32 (space) ends up displayed as some character like Ġ. Building the dict as {display_char: original_byte} and running every character of a raw vocab token through it, then decoding the resulting byte string as UTF-8, is exactly GPT-2's/BPE's published byte-to-unicode scheme run in reverse — turning "Ġcat" back into " cat".

Why this had to be hand-built

The subject bans transformers' high-level tokenizer conveniences from the decision-making pipeline. sdk.get_path_to_vocab_file() only hands you the raw file — turning its contents into real characters your grammar can reason about (state_tracker checks things like "is this character a digit", which is meaningless on a raw "Ġcat"-style string) is exactly the kind of "from scratch" work the project is graded on.

The result is a VocabularyManager — a bidirectional id_to_token / token_to_id pydantic model — built once per run and threaded through everything downstream that needs to go from a token ID the model produced back to the literal text it represents.

04 · src/orchestrator.py

04The Pipeline: One Loop, One Shared Deadline

run_pipeline is the conductor. It loads the catalog, the prompts, and the vocabulary (Sections 02–03), then for every prompt: builds a natural-language instruction string (build_prompt), calls into decoder.py, and hands the result to output.py to be validated and either accepted or downgraded to a best-effort fallback. Nothing in this loop ever raises past itself — every failure mode is caught and converted into a result record, because the contract is "every prompt produces exactly one output row," full stop.

build_prompt: the only place natural language is authored

This function is deliberately not part of the decoding algorithm. It hands the model a plain-text system-style instruction, with the full function catalog rendered as name(params): description lines and two worked examples — including one deliberately tricky regex example, teaching the model the difference between a literal substring and a pattern before it ever sees a real prompt. This is prompt engineering, not grammar engineering: it improves the odds the model's logits point at the right function and the right values. It has zero influence on whether the output is valid JSON — that guarantee comes entirely from decoder.py, independent of how good or bad this prompt text is.

A precise way to say this to an evaluator

Accuracy (picking the right function, the right numbers) is a prompt-engineering and model-capability problem — build_prompt's job. Validity (the output parses, matches the schema, uses declared parameter names and types) is a decoding-algorithm problem, solved once, independent of prompt quality — that's the whole point of constrained decoding.

The shared deadline — and the "everything after becomes unknown" behavior

This is the mechanic you flagged as something you don't love. Here is exactly what it does and why, so you can decide with full information whether to leave it as-is (which is a legitimate choice) or change it.

src/orchestrator.pyrun_pipeline()
start = time.time()
deadline = start + config.time_budget_seconds   # one fixed point in time, computed once

for i, item in enumerate(prompts, start=1):
    if time.time() >= deadline:
        result = assemble_fallback_result(item.prompt, catalog, "")
        # ... report + append, then `continue` to the next prompt

Notice deadline is computed once, before the loop starts, as an absolute point in wall-clock time (start + time_budget_seconds) — not a per-prompt timer that resets. time.time() is monotonically increasing (it never goes backwards mid-run). So the check time.time() >= deadline, once it becomes True for one prompt, is mathematically guaranteed to stay True for every remaining prompt in the batch — there is no code path by which it could become False again later in the same run. That is exactly the behavior you noticed: one slow prompt (or a few) exhausts the budget, and every prompt after it falls straight to assemble_fallback_result(item.prompt, catalog, "") — empty partial text, no name recoverable, so name="unknown", parameters={} — without the decoder ever being invoked for them, even if any individual one of those remaining prompts would have finished in well under a second.

This is a design choice, not a bug — but it's the wrong shape of budget

It correctly guarantees the subject's "process the whole test set in under 5 minutes" requirement: worst case, the batch stops doing real work the instant the shared budget is spent. Its weakness is exactly what you noticed: the budget is spent, not redistributed. A batch-level deadline with no per-prompt allowance means one pathological prompt can "poison" every prompt queued after it, even though the population's average cost per prompt is nowhere near the limit. A straightforward, still-simple improvement — worth mentioning if asked "how would you improve this" — is giving each remaining prompt its own slice of the remaining budget: e.g. per_prompt_deadline = min(deadline, time.time() + (deadline - time.time()) / remaining_count), recomputed every iteration. That preserves the same hard ceiling on total time while letting individual fast prompts still get a fair shot even after a slow one.

Two other things worth being able to narrate: GenerationIncomplete (raised by decoder.py when it runs out of tokens, hits the deadline mid-generation, or the masker finds zero legal tokens) always carries whatever text was generated, in e.partial_text — that's what lets assemble_fallback_result attempt best-effort recovery via regex instead of giving up entirely. And the broad except (OSError, ValueError, RuntimeError) clause is exactly the PipelineError tuple again, this time caught per prompt rather than around the whole program, so one malformed model output can't take down the entire batch.

05 · src/output.py

05From Generated Text to a Trustworthy Verdict

It is tempting to assume that because decoder.py guarantees valid, schema-compliant JSON, output.py's job is trivial. It isn't skipped, and that's intentional: assemble_result re-parses and re-validates the generated text completely independently of the decoder's internal state — checking JSON validity, the exact {"name","parameters"} key set, that the name exists in the catalog, that the parameter key set exactly matches the function's declared signature, and that every value's runtime Python type matches its declared schema type (with a deliberate special case: bool is a subclass of int in Python, so _value_matches_declared_type explicitly rejects a bare True/False from silently passing as an "integer").

Why re-validate what the decoder already guaranteed?

Defense in depth, and a genuinely good engineering habit to name out loud: the decoder's guarantee is only as good as the decoder's own code being bug-free. Re-validating downstream, from the generated text alone, with zero knowledge of decoder internals, means a subtle decoder bug gets caught here — as a clear ValueError naming the exact prompt and field — instead of silently corrupting the output file.

The two normalization helpers matter for exactness: _coerce_value forces a JSON integer that's semantically a "number" parameter into a real Python float (so 3 becomes 3.0 in the output, matching the declared type precisely), and _strip_copied_quotes cleans up a common small-model artifact — copying a quoted word straight out of the prompt, quote marks and all, into a string argument.

The fallback path: best-effort salvage, never a crash

When generation is incomplete, assemble_fallback_result runs two regexes against whatever partial text exists: _extract_partial_name looks for a complete "name": "..." pair, and _extract_partial_value looks for a complete "key": value pair per declared parameter. Anything not found — including, deliberately, anything cut off mid-token — becomes the literal string "unknown", and if not even the function name can be recovered, the whole record becomes {"name": "unknown", "parameters": {}}. This is the single mechanism producing every "unknown" you see in your output — both the "ran out of time budget entirely" case from Section 04 and the "decoder started but didn't finish this one prompt" case funnel through this exact same function.

06 · src/decoder.py — the heart of the project

06decoder.py: The Constrained-Decoding Engine

Everything so far has been plumbing around one core idea, and it's worth stating that idea in one sentence before touching a line of code:

The core idea

At every single generation step, instead of asking the model to produce valid output and hoping, the program first computes the complete set of tokens that could legally come next given everything generated so far — and forcibly sets every other token's logit to -inf before the model is even allowed to pick. The model only ever gets to choose which legal continuation it prefers, never whether to be legal.

This is implemented as two independent, stacked layers of "what's legal here", kept deliberately separate in the code:

Layer 1 — state_tracker

A pure JSON grammar automaton. Knows nothing about function names or parameter types. Answers only: "is this character syntactically legal JSON right now?" (balanced braces, quotes, colons, commas, valid number/string/literal shapes per RFC 8259).

Layer 2 — schema_resolver

Wraps Layer 1. Knows about the live FunctionCatalog. Answers the narrower question: "of the characters Layer 1 would allow, which ones are also consistent with the exact two-key shape, the closed set of real function names, and the selected function's declared parameter names/types?"

Why split it this way instead of one big function is Section 07's whole subject — hold that thought and first understand each layer on its own.

6.1 — The JSON automaton: Pos and state_tracker

Pos is an Enum naming every distinct "place" the grammar can be in: expecting a root value, inside an object expecting a key-or-close-brace, past a colon expecting a value, inside a string, mid-escape-sequence, mid-number, mid-literal (true/false/null), and so on. What makes this a real formal-grammar engine rather than a flat switch statement is that f1_state — the variable passed around everywhere as state or stack — is literally a stack (a Python list), and _descend pushes a new frame onto it every time a new JSON value begins:

src/decoder.py_descend()
def _descend(stack: list, char: str) -> List | None:
    """Push the state entered by starting a new value with `char`."""
    if char == "{":      stack.append(Pos.OBJ_KEY_OR_CLOSE)
    elif char == '"':    stack.append(Pos.IN_STRING)
    elif char == "-":    stack.append((Pos.IN_NUMBER, "start_needs_digit"))
    elif char == "0":    stack.append((Pos.IN_NUMBER, "leading_zero"))
    elif char.isdigit(): stack.append((Pos.IN_NUMBER, "digits"))
    elif char in _LITERALS: stack.append((Pos.IN_LITERAL, _LITERALS[char][1:]))
    else: return None
    return stack

This makes state_tracker a pushdown automaton (PDA), not a plain finite-state machine — the distinction is precisely why it can correctly handle arbitrarily nested {...} without any hardcoded depth limit: entering an object pushes a frame, closing one ("}" in OBJ_COMMA_OR_CLOSE or OBJ_KEY_OR_CLOSE) pops it, and the automaton's "current state" is always just stack[-1]. Popping back to the parent's own pending state after a nested value finishes is exactly what a plain FSM cannot express and a PDA can.

Watch the number sub-machine specifically — it's the trickiest part of the JSON grammar and the part most people get subtly wrong by hand:

"digits"
IN_NUMBER
after "12"
"dot_needs_digit"
IN_NUMBER
after "12."
"frac_digits"
IN_NUMBER
after "12.3"
OBJ_COMMA_OR_CLOSE
number frame popped on "," or "}"

Each of the four number sub-states enforces one real JSON rule that's easy to get wrong: "start_needs_digit" forbids a bare trailing minus sign; "leading_zero" forbids "012" (JSON disallows leading zeros — only a lone 0 or 0.x is legal) by only accepting a following ".", never another digit; "dot_needs_digit" forbids a trailing bare dot like "12."; and when a non-digit, non-dot character finally arrives, the number frame is popped (stack.pop()) and the same character is re-dispatched (return state_tracker(stack, char)) into whatever state now sits below it — that's how a number cleanly hands control back to "comma-or-close" without the caller needing to know the number just ended.

6.2 — The schema overlay: SchemaState and schema_resolver

SchemaState is a small dataclass tracking everything Layer 1 doesn't know about: which function has been selected so far (None until the "name" string is complete), which of its parameters are still remaining_params, the declared type of whichever parameter value is currently being written, and a live buffer used to match partial strings — a function name or a parameter key — character by character against the legal pool.

schema_resolver(f1_state, f2, char) is where the two layers actually meet. Read it as a sequence of guards (early return Nones representing "no, not here") followed by a call into state_tracker, followed by bookkeeping that advances f2 based on what just became true. The single most instructive guard is this one:

src/decoder.pyschema_resolver() — closed-set name matching
if (prev_top == Pos.IN_STRING and char != '"'
        and f2.collecting in ("name", "key")):
    candidate = f2.buffer + char
    pool = (
        [fn.name for fn in f2.catalog.functions]
        if f2.collecting == "name" else list(f2.remaining_params))
    if not any(name.startswith(candidate) for name in pool):
        return None   # no real function/param name starts this way — illegal

This is the mechanism that makes function selection itself part of constrained decoding, not a separate heuristic step run before or after it. While the model is writing the "name" string one character at a time, every candidate character is checked against "is there at least one real function name that starts this way" — so the model can never wander off into inventing a function that doesn't exist; it is only ever choosing among the real, declared names, and it is the model's own logits — via token_selector's greedy argmax over whatever legal characters/tokens survive — that decide which real name wins. The exact same mechanism, reused unchanged, disambiguates parameter keys once inside "parameters": {...}.

The rest of schema_resolver's guards enforce, respectively: the two root keys must appear as literally "name" then "parameters", in that order, and no third key is ever legal; once "parameters"'s colon is written, the very next non-whitespace character must be { (no scalar "parameters" value is ever allowed); a value inside parameters must start with a character legal for that key's declared type (_value_start_allowed — a string parameter can only ever start with ", a number/integer only with a digit or -, a boolean only with t/f); a comma inside parameters is illegal while parameters remain unfilled and the closing } of parameters is illegal while any are still missing (both directions of "you must supply exactly the declared parameters, no more, no fewer"); and backslash-escaping is deliberately forbidden entirely inside the "name"/key/root-key strings (real names never contain a backslash, so allowing one there is pure attack surface with zero benefit) while still permitted, with a 2-backslash lookback guard against runaway \\\\\\... sequences, inside ordinary string values.

The part that looks like complexity for its own sake — but isn't

This function is dense. Every guard in it maps to one sentence of the function-calling schema (not the JSON grammar — that's Layer 1's job), and every one of those sentences is a real requirement from the subject: exact key names, exact key order, exact parameter set, exact types, real function names only. If an evaluator asks you to justify any single if in this function, you should be able to answer "this is what stops the model from doing X, and X would violate requirement Y."

6.3 — Making it fast: the vocabulary trie and cached transitions

Here's the performance problem this project actually has to solve: Qwen3-0.6B's vocabulary has on the order of 150,000 tokens. Naively, checking "is this token legal" for every one of them, at every single generation step, by re-running schema_resolver character-by-character over each token's full string independently, would mean redoing the same work for every token that happens to share a prefix — and nearly all of them do, since the vocabulary is built from a small alphabet.

build_vocab_trie solves the "shared prefixes" half of this: it's built once, before generation starts, as a nested dict where each edge is one character and each terminal node lists every token ID whose full string ends exactly there. Then logit_masker walks this trie recursively alongside the automaton, advancing both one character at a time — so a common prefix shared by thousands of tokens is validated against schema_resolver exactly once, and every token that shares it inherits that answer for free by simply continuing to whichever branches remain reachable.

src/decoder.pylogit_masker() — trie walk with memoized transitions
def walk(node: dict, state1: list, state2: SchemaState) -> None:
    terminal = node.get(None)
    if terminal: legal_ids.extend(terminal)
    for ch, child in node.items():
        if ch is None: continue
        key = (_state_key(state1, state2), ch)
        if key in transition_cache:
            result = transition_cache[key]
        else:
            result = schema_resolver(state1, state2, ch)
            transition_cache[key] = result
        if result is not None:
            walk(child, *result)

_state_key then solves the "same state visited more than once" half: it turns (f1_state, f2) into a hashable tuple, so transition_cache[(state_key, char)] memoizes "from this exact automaton+schema state, does character c lead anywhere legal" across the whole trie walk — and, since the cache is created once per call to generate_function_call and threaded through every step, across the entire generation of one prompt. States genuinely do repeat a lot in this grammar (e.g. every time the model is inside a generic string value with no further constraint, or every time it revisits OBJ_COMMA_OR_CLOSE at the same depth), so this cache is doing real, measurable work, not just defensive tidiness.

Without trie or cache

~vocab_size × avg_token_length individual schema_resolver calls per generation step.

Trie only

Shared prefixes validated once; work scales with the trie's actual branching, not raw vocab size.

Trie + transition cache

Repeated (state, char) pairs across the whole prompt's generation are computed once, ever.

6.4 — Putting it together: the generation loop

generate_function_call is deliberately short, because everything hard has already happened in the three building blocks above. Each iteration: check the shared deadline (Section 04); call sdk.get_logits_from_input_ids for the raw, unfiltered logits over the whole vocabulary; call logit_masker to set every illegal logit to -inf; call token_selector, which is a plain argmax — deterministic, greedy, no sampling — over what survives; then, critically, walk the chosen token's string one character at a time through schema_resolver again to actually commit the state transition:

src/decoder.pygenerate_function_call() — the loop body
logits = sdk.get_logits_from_input_ids(input_ids)
masked = logit_masker(logits, trie, f1, f2, transition_cache)
token_id = token_selector(masked)                 # argmax, deterministic
token_str = vocab.id_to_token[token_id]

for char in token_str:                        # tokens rarely align to 1 JSON char
    result = schema_resolver(f1, f2, char)
    if result is None:
        raise GenerationIncomplete(f"Masker selected illegal token {token_str!r}", ...)
    f1, f2 = result

generated_text += token_str
input_ids = input_ids + [token_id]

That inner for char in token_str loop is not incidental — it's the fix for a real problem named directly in your own README's Challenges section: BPE tokens almost never align one-to-one with one JSON-grammar-relevant character. A single token might be 'multiply' (eight characters at once), or a number and a comma fused together, or half of an escape sequence. Re-running the character-level resolver here — the exact same function already used for masking — guarantees the committed state is always correct regardless of how the tokenizer happened to chunk the text, and the if result is None: raise GenerationIncomplete(...) is a deliberate "should never happen" assertion: if the masker did its job upstream, every token that survives masking is guaranteed to be re-walkable here without failure. Its only purpose is to convert a silent internal contradiction into a loud, diagnosable one.

Termination is equally direct: f1 == [Pos.ROOT_DONE] means the root value (the whole {...} object) closed and the stack unwound completely — the JSON is syntactically finished, and because Layer 2's guards were active the entire way, it is also schema-complete by construction. If that never happens within max_new_tokens (150), or the shared deadline hits mid-generation, or the masker ever produces zero legal tokens (an internal bug, not a model failure), the loop raises GenerationIncomplete carrying whatever text exists so far — which is exactly the object Section 04/05's fallback path consumes.

07 · The question that matters most

07Grammar + Schema vs. "Just Hardcode the Blueprint"

This is the comparison an evaluator is most likely to push on, because the alternative genuinely looks simpler on paper: once the model has picked a function, you already know — from functions_definition.json — the exact literal skeleton the rest of the JSON has to be. Why not just template it?

What the "hardcoded blueprint" approach would look like

Concretely: pick the function first (by whatever means), then build a literal target string like '{"name": "fn_add_numbers", "parameters": {"a": ' character-for-character, and at each generation step, mask every logit except the one token that continues that exact literal string. When you hit a value slot, mask to that parameter's type-specific characters (digits for a number, " to open a string) instead of a literal, then resume the literal skeleton for the closing punctuation. This is "inject the JSON schema directly" — the blueprint is a hardcoded string template per function, built from the schema once, ahead of generation.

The one problem this approach can't dodge

It needs to know which function it's templating before it can write a single character of the template — but choosing the function is the core task the model has to solve from the prompt. If the blueprint approach picks the function by any means other than letting the model's own logits choose among the real names character-by-character during generation (exactly what your "name"-collecting guard in Section 6.2 does), it has smuggled in a heuristic or a separate classification pass — which is precisely what the subject's "function selection performed entirely by the model's own logits, no keyword matching or heuristic routing" requirement forbids. To stay compliant, a blueprint system still needs a closed-set-constrained free generation phase for the "name" field before any blueprint can be selected — at which point it has already reinvented a miniature version of your Layer 2.

So which is "smarter"?

Not a matter of taste — it follows directly from what the subject is actually testing. The assignment isn't "produce valid JSON for six known functions" (a blueprint would ace that); it's "build, from raw logits, the mechanism that makes producing invalid output impossible, without leaning on structured-generation libraries, and without the model's function choice being decided by anything other than the model." A hardcoded blueprint answers the first framing extremely well and the second framing only by smuggling back in the exact free-form, closed-set-constrained generation step your project already implements as Layer 2's name-matching guard. In other words: the hardcoded approach isn't a simpler solution to the same problem — it's a solution to an easier problem that quietly assumes the hard part (function selection) is already solved. Your version solves the actual problem: general JSON legality as a reusable, schema-independent foundation, with the specific schema constraint as a thin, swappable overlay on top — the same layering real constrained-decoding systems use, built by hand.

The honest cost is real, though, and worth stating plainly rather than glossing over: your approach is more code, has a larger surface for subtle bugs (the guard-clause density in schema_resolver is the main risk), and is slower per token than a literal continuation would be. None of that is free. It's the correct trade for what's being graded here.

08 · Rehearsal

08Defending It Live — Anticipated Questions

Why is f1_state a list instead of just a single enum value?

Because JSON is a recursive, nestable grammar and a single current-state value can't remember what to return to after a nested value closes. The list is a stack: entering any value pushes a frame (_descend), and closing one pops it, restoring exactly the parent's pending state. This makes it a pushdown automaton, not a flat FSM — the only structure that can correctly parse arbitrarily nested braces without hardcoding a depth limit.

Why is decoding greedy (argmax) instead of sampling with temperature?

Because there is no notion of "more interesting" output for this task — a function call is either the correct one or it isn't, and once logits are masked to the legal set, sampling would only add variance with no upside. Greedy selection is also what makes a run reproducible: the same prompt always produces the same output.

What happens if the model "wants" an illegal token more than any legal one?

It never gets the choice. logit_masker sets every illegal token's logit to -inf before token_selector's argmax runs, so illegal tokens are mathematically excluded from the selection, not merely disfavored. This is the entire meaning of "producing malformed JSON becomes impossible rather than merely unlikely" from your README.

How do you guarantee the model can't invent a function or parameter name that doesn't exist?

While a name or key is being collected character-by-character (f2.collecting in ("name","key")), every candidate character is checked against "does at least one real function name / remaining parameter name start with this prefix"; if none do, that character is illegal and its tokens are masked out. The model is structurally confined to the real, declared identifiers the entire time it's writing one.

Why validate everything again in output.py if decoder.py already guarantees correctness?

Defense in depth: the decoder's guarantee is only as strong as the decoder's own code. Re-parsing and re-validating the generated text independently, with zero shared state, means a subtle bug in the 475-line decoding engine gets caught as a clear, prompt-specific error message here rather than silently corrupting the output file. It's cheap insurance against exactly the kind of bug that dense stateful code like schema_resolver is most prone to.

Why does one slow prompt turn every remaining prompt's result into "unknown"?

The time budget is a single fixed wall-clock deadline for the whole batch, computed once at the start (start + time_budget_seconds), not a per-prompt timer. Since wall-clock time only moves forward, once time.time() >= deadline is true for one prompt it is true for every prompt after it, so the loop correctly stops attempting real generation and every remaining prompt falls to the same empty-partial-text fallback, which resolves to name="unknown". It's a deliberate, simple way to guarantee the subject's "under 5 minutes for the full set" requirement can never be violated; its known trade-off is that it doesn't redistribute leftover budget across the remaining prompts individually.

Does your grammar support nested objects or arrays as parameter values?

Layer 1 (state_tracker) can parse arbitrarily nested {...} structurally — that's inherent to it being a real PDA. What's deliberately scoped out is Layer 2: ParamType only declares string / number / integer / boolean, and _value_start_allowed only recognizes scalar value starts, so a nested object or array is never a legal parameter type in this project's schema — not because the grammar layer couldn't support it, but because the function catalog format never declares one. Extending it would mean adding an "object"/"array" case to ParamType, PYTHON_TYPE_BY_PARAM_TYPE, and _value_start_allowed — no change needed to Layer 1 at all.

Why build a trie instead of just checking every vocab token independently?

Because most of the ~150k tokens in Qwen3's vocabulary share long common prefixes. Walking a trie alongside the automaton means a shared prefix is validated against schema_resolver exactly once for every token that shares it, instead of redundantly re-deriving the same answer per token. The transition_cache on top of that memoizes repeated (state, character) pairs across the whole generation of one prompt, since the same automaton states recur constantly (e.g. every generic string character, every revisit of "comma or close").

09 · Intellectual honesty

09Honest Weak Points — Know Them Before They're Asked

A defense that only lists strengths reads as rehearsed rather than understood. These are real, named trade-offs in the current implementation — naming them unprompted is itself evidence of mastery.

Shared, non-redistributed time budget

Covered in depth in Sections 04 and 08 — one exhausted deadline cascades to every remaining prompt regardless of their individual cost.

Guard-clause density in schema_resolver

~15 early-return guards in one function is a real maintainability cost; a bug here is the single most likely place for a subtle correctness issue to hide, which is exactly why output.py's independent re-validation exists as a safety net.

Greedy decoding forecloses recovery

Because selection is always argmax with no backtracking, if the model's top legal choice at some step leads toward an accurate-but-suboptimal completion, there's no mechanism to reconsider — unlike beam search, which the subject's scope doesn't require but which would be a legitimate accuracy improvement to mention.

Flat scalar parameters only

Deliberately scoped, and defensible (see the nested-objects Q&A above), but it is a real scope limitation of Layer 2, not a limitation of the grammar itself.

Per-step cost still grows with vocabulary size

The trie and cache reduce redundant work dramatically, but every generation step still walks live trie branches; a pathologically branchy state (e.g. very early in a generic string value) still visits more nodes than a template's O(1) literal lookup would.

Fallback parameters are string "unknown", not typed

In assemble_fallback_result, an unrecoverable parameter becomes the literal string "unknown" even for a declared number or boolean parameter — a deliberate, honest "we don't know" marker, but one a strict downstream consumer expecting the declared type would need to handle explicitly.
